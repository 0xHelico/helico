## The shape

```
browser ──▶ apps/app  /api/chat ──▶ apps/be  POST /api/swap/intent ──▶ model
                │                       │
          Reown AppKit            the token registry, which checks
          (wallet only)           what the model proposed
```

Three things follow from that arrangement, and each is the reason for it:

- **The browser never learns the backend's address.** The chat route is a server route, so
  `BE_API_URL` stays on the server and there is no cross-origin request to configure.
- **The model does not decide anything.** It reads a sentence and proposes a symbol pair
  and an amount. `apps/be` looks the symbols up in a registry of addresses verified on
  chain and refuses anything it does not recognise. The app renders what came back and
  never re-derives it.
- **The wallet is the only identity.** No email, no social login, no vendor account. A
  wallet-only app has no session to steal, and no user rows to lose.

## Done in this pass (PR #128)

- The template pruned: auth, artifacts, documents, votes, Postgres, Redis, the AI SDK
  providers and the file uploads all removed. What remains is a chat surface.
- Reown AppKit on Arbitrum One, `features: { analytics: false, email: false, socials: false }`.
- The chat route, the intent card, and the sentence that says signing is not wired yet.
- `ncu -u` inside `apps/app` only.

Verified in a browser against a local `apps/be` built from #115 with a real model key: the
modal lists 310 wallets and no email field, "Swap half an ETH into USDC" returns the
checked intent, the card shows Arbitrum One and `500000000000000000`, the honesty line
renders, and the console is clean.

## Not done, and what each one waits on

| Missing | Waits on |
|---|---|
| Reading the connected address's position and mandate | the vault on a live network (#85) |
| `approve`, `setMandate`, `revoke` | the same |
| Signing and sending the intent | the same |
| EIP-712 sessions in `apps/be` | a reason to have one — see below |
| The deploy to `app.helico.site` | the deploy pattern the landing and docs already use |

**On sessions.** The owner asked for EIP-712 *"if it needs a session"*. It does not yet.
Nothing in the app is per-user: the chat holds no history, there is no profile, and the
intent is derived fresh from each sentence. Adding a signed session now would be a login
protecting nothing. The moment chat history or a saved profile arrives, the session is the
first thing to build, and the shape is already decided: a typed `Session` struct signed
once, the address recovered in `apps/be`, and a short-lived cookie after that.

## Deploying it

The same path as the landing and the docs, which is already proven: a Dockerfile in
`apps/app`, a GHCR image built on merge, and the SSH forced command asking Coolify to
redeploy. Next is configured `output: standalone`, so the runtime stage copies
`.next/standalone` and runs `server.js` as a non-root user. `BE_API_URL` is a build-time
argument with `https://api.helico.site` as its default in the Dockerfile — the landing
taught us that an argument passed only by the workflow silently does not arrive.

## What this pass deliberately did not upgrade

`ncu -u` was run in `apps/app` and nowhere else. `contracts/`, `apps/cre` and
`packages/plugins/*` hold the two partner integrations that are verified working, and the
root's TypeScript 5→7, bun 1.3→1.4, zod 3→4 and jsbi 3→4 bumps would put those at risk six
days before the deadline for no gain the judges can see.
