# The blog API on the VPS

## What

`apps/be` at `https://api.helico.site`, deployed the way the landing and the docs are: a
Coolify application in the helico project built from this repository's `apps/be/Dockerfile`,
published on `127.0.0.1:3024`, fronted by the host nginx with a Let's Encrypt certificate
obtained as the user, and redeployed on every merge that touches `apps/be` through the SSH
forced command from #108 (the command's map gains `api`).

## The image

Two stages: `golang:1.25-alpine` builds a static binary (`CGO_ENABLED=0`, trimmed, stripped;
the SQLite driver is pure Go). The runtime is `alpine:3.21` with a dedicated non-root user, the
binary, the Markdown content for seeding, `wget` for the health check, and `/data` owned by
that user for the SQLite file. `/data` is a Coolify persistent volume, so the database survives
redeploys; the Markdown in the image seeds only what the database does not already hold.

## Configuration

`BE_ADDR=:8787`, `BE_DB_PATH=/data/helico.db`, `BE_CONTENT_DIR=/app/content` in the image;
`BE_CORS_ORIGINS` (the landing's origins and the local dev ports) and `BE_ADMIN_TOKEN` as
Coolify environment variables, the token generated on the server and never printed. The
automation repository's `.env` gets the same token and `BE_API_URL`, so `blog:publish` can
write posts.

The landing's Coolify application gets a build-time `BE_URL=https://api.helico.site`, and its
Dockerfile passes it through, so the blog is built from the API when it answers and from the
files when it does not (`posts.ts` already falls back). Published posts reach the blog on the
landing's next rebuild.

## Verification

The image built by Coolify from the pushed branch; `/healthz` and `/api/posts` answering on
the loopback port and on `https://api.helico.site`; a `PUT` with the token answering `201`
and the post visible on `GET`; a landing rebuild with `BE_URL` listing the API's posts.
